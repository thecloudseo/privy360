Build the permanent modular-monolith product as **system of regulation + system of record + system of action + system of evidence**. The executive proof is: “Can I prove, right now, that this organization is operating its DPDP controls?” The relational Compliance Evidence Graph connects law, versioned requirement, control, processing activity, data, system, vendor/processor, principal, consent, evidence, risk, task and audit. The bid is an early production-quality scope milestone, not a smaller architecture. No microservice, Kafka, graph database or external search dependency is introduced by scheduling.

The baseline request path is browser → ingress/WAF → Next.js web/BFF → NestJS authenticated trusted context → deterministic RBAC/ABAC and object scope → domain service → PostgreSQL transaction with business state, minimal audit and outbox. Workers consume durable events and use Temporal for long-running workflow coordination; Temporal is not the business record. AI and connectors are authorized, policy-bound adapters. All tenant-owned rows carry explicit tenant ownership and RLS; no browser-supplied tenant proves membership. Immutable images, SBOM/vulnerability/secret/IaC gates, synthetic development data and human security approval for production-sensitive actions remain invariant.

## 2. Execution rules and release labels

- **BID-BLOCKING** means every B ticket in the index, including `HARDEN-001`, must pass its ticket acceptance and inherited T0–T5 checks for Release 0.1. The 67 remaining B cards are non-optional; `REPORT-003` is not the sole gate. **POST-BID** means P/F/L work. No P/F/L ticket is silently promoted into the bid. **BID-IMPORTANT** is reserved for a future explicit release-scope decision; none is currently marked that way, preserving the approved exact B set.
- The revised index is a valid topological order and §4 is its CP0 decision record. A card may be designed against a frozen upstream contract in another branch; it cannot integrate before its **approved** hard dependencies and named contract freezes pass. “Drafting against a contract” is not a completed ticket.
- A wave is an **execution window of parallel lanes**, not a claim that each card in a lane starts simultaneously. The first ready card in each lane may run concurrently; a later card in that lane activates only after its own prerequisites pass. This avoids 60-plus one-ticket windows while preserving every approved edge. The ledger lists each ticket once and its exact approved dependencies and direct dependents.
- Each ticket gets a scoped implementation plan before code: exact owner files, frozen API/schema/event/auth contract, negative tests, migration/rollback where needed, T0–T5 applicability, acceptance criteria and security decision boundary. No ticket is broadened by an adjacent directory. A plan challenge is a bounded pre-implementation check, not a recurring architecture review.
- Contract changes are owned by one lane. Consumers may use versioned/generated contracts in parallel. Shared `packages/contracts`, migration order, `packages/auth`, audit/outbox, identity and common API middleware each have one writer at a time; other lanes submit contract proposals to the owner. Contract compatibility tests precede integration.

## 8. Model and skill routing

The ticket ledger assigns one recommended execution class per ticket: `LL` = `gpt-6-luna` Low for deterministic/config/test subtasks; `LM` = `gpt-6-luna` Medium for isolated ordinary features; `SM` = `gpt-6.1-sol` Medium for coordinated API/UI features; `SH` = `gpt-6.1-sol` High for database/auth/security/CI/deployment and multi-owner reasoning; `SX` = `gpt-6.1-sol` Extra High or `gpt-6-astra` High/Extra High only for difficult critical remediation or independent boundary review. No whole ticket currently receives `LL` or `SX`; their use is task-specific. A class is a cost/quality starting point, not permission to relax tests. Chief Architect checkpoints use Astra High/Extra High only where the listed decision actually requires it.

Skill routing is deterministic: **Superpowers** for planning, debugging, TDD, verification, code review and finishing at the appropriate phase; **Enterprise Engineering Toolbox** for repository/architecture/security/API/database/deployment judgment when those boundaries appear; **Full-Stack Engineering Expert** for actual TypeScript/Node/React/Nest/database/test/deployment implementation; **Token Optimization** for substantial repository inspection, large logs/evidence and multi-step tasks; **frontend-design** only when genuine visual design or UX implementation/review is required (`FOUNDATION-006`, relevant UI surface cards). Do not activate every skill by default. The ledger's `UI` marker signals where frontend-design may be useful, not mandatory for purely contract/API work.

Every future execution prompt emits `MODEL / REASONING: <ledger class → exact model/effort> — <one sentence citing the ticket's impact flags and boundary>` and `SKILLS TO USE: <only the phase-appropriate skills above, each with a specific role>`. Superpowers must name the workflow role, such as writing the ticket plan, systematic debugging, TDD or verification; it is not a generic endorsement. Full-Stack Engineering Expert is omitted for pure repository/architecture review. Token Optimization is included when repository/tool inspection or evidence volume is substantial. UI-only visual design triggers frontend-design; an API or contract with no visual work does not.

Verification shorthand in the ledger: `T0` always; `D` means T1 migration/RLS/rollback; `C` or `A` means T2 API/domain/auth positive and negative contract/object/field/audit tests; `W` means T3 worker/external retry/crash/reconciliation; `U` means T4 UI E2E, accessibility, Hindi/English and denied-scope; `S` means T5 independent adversarial security review before production acceptance. The ticket card supplies the exact acceptance tests. `P` marks deployment impact and adds image/SBOM/IaC/secret/config/restore checks as applicable. A blank marker never waives the inherited mandatory envelope.

## 10. Velocity guardrails and progress

1. Freeze finite acceptance and inherited T0–T5 applicability before code. Review the acceptance, not an expanding wish list. A material safety/correctness defect can still block closure.
2. Classify each new finding in the ticket/PR: **current-ticket correctness defect**, **current-ticket security blocker**, **follow-up ticket** (new explicit ID and dependency), or **backlog/hardening**. Owner and evidence accompany classification. A reviewer cannot silently append unrelated scope to a completed card.
3. A new third-party CVE does not reopen a completed architecture ticket when its enforced assumption still holds: retain finding, deny unapproved local use, apply unchanged production gate, and create a bounded image/remediation/disposition follow-up. A bypass of those controls is a blocker.
4. Checkpoints are CP0–CP11 triggers above. Ordinary cards use CI/contract/unit/integration/E2E/security tests and normal code review. Production human/security approval is never inferred from ticket completion.
5. Production hardening is strict at its release gate; a development-only component is not falsely labelled production-approved. No bypass for demonstration. Unknown legal mapping stays explicitly synthetic.
6. Track each ID in one status ledger (`not-started`, `contract-frozen`, `implementing`, `integrating`, `verified`, `accepted`, `blocked`) with current branch/commit, owner, declared and optimized dependencies, wave, test evidence, checkpoint, decision and blocker link. Update status only from merged/reviewed evidence; the appendix is the initial inventory, not a substitute for ticket cards.
