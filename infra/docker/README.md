# Local portable services

This stack is eligible only for isolated local development under [ADR-034](../../DECISIONS/ADR-034.md). It is not vulnerability-free and is not approved for production, customers, government deployments, staging under production policy or release bundles. No individual vulnerability disposition is active. The local eligibility checker therefore currently fails closed. The production/deployable High/Critical gate is unchanged.

`pnpm services:up` enforces local eligibility before launching any service. A cached preflight denies known High/Critical findings without active dispositions; when preflight permits an attempt, fresh image scanning and SBOM collection must succeed in the same process as the eligibility decision. While the disposition register is empty, normal startup is intentionally denied. The earlier FOUNDATION-003 functional verification used a bounded temporary stack before this final admission gate was attached; those containers were shut down with volumes retained.

`pnpm test:cp1-postgres` is a test-only, service-scoped CP1 verifier. It applies the same reviewed image, digest, platform, boundary validator, fresh Trivy/Syft collection and zero-High/Critical admission rule to `app-db`; it does not admit Keycloak, Redis or the full stack. Its sole Compose configuration delta changes `app-db.environment.POSTGRES_USER` from `privy360_app` to `privy360_cp1_bootstrap`, because PostgreSQL 18's initialization role is the non-demotable OID-10 bootstrap superuser. The verifier applies the canonical migrations through that privileged initialization boundary, transfers only Privy360 database objects to `privy360_migrator`, and runs isolation assertions as the separately created non-owner `privy360_app`. It uses synthetic data and credentials, publishes bounded evidence only after all assertions and cleanup pass, and removes its disposable project and volume on success or failure. This profile is not an alternate application startup path or production approval.

All service images are pinned by digest and to `linux/amd64` in Compose and [the reviewed inventory](security/images.json). Resource and process limits are checked by the local boundary validator. No host ports are published; all Compose networks are internal. These limits were exercised in the local startup/restart test, but are not production sizing. Docker cannot prevent a developer from creating a host tunnel, entering real data, or configuring federation through Keycloak after startup. Those actions are prohibited for this stack and require operational review. Do not import untrusted realms, custom providers or themes.

The `security/evidence/` collection retains Trivy and Syft original output, the requested OCI index and selected linux/amd64 manifest, full SBOM provenance, compact summaries and checksums. The separate historical Keycloak scan remains labeled as a September 30 assessment. A collection must pass the supported scanner schemas, minimum package coverage, the reviewed current known-finding floor (23 Keycloak, four Redis), and image/config identity chain before atomic publication. That floor detects truncated vulnerable scans; newly discovered findings remain visible and denied. A reviewed image/policy update is required when a legitimate fix changes the known count. The image policy itself is part of the material binding. Completed scans with unapproved findings are published and eligibility is denied; failed or partial collections leave accepted evidence unchanged. Scanner overrides inherited from the environment are stripped. Collection has a 600-second deadline. `pnpm services:security:collect` collects without granting eligibility; `node scripts/local-image-evidence.mjs validate` checks cached integrity without granting eligibility; `node scripts/local-image-evidence.mjs evaluate` denies cached assessment as proof of a current scan.

The empty `security/dispositions.json` is intentional. Local dispositions require an exact Ed25519 signed approval manifest with the approved occurrence, material binding, evidence checksums, dates and revision. Verification uses a protected trust record outside this repository, owned independently of the executing agent. That trust record must identify the reviewer key fingerprint, minimum accepted revision per approval reference, and revoked manifest digests. No operational trust record or real reviewer key is provisioned by FOUNDATION-003; synthetic keys exist only in tests and cannot be loaded as operational authority. Approval strings in a disposition are insufficient. The future independent reviewer must provision this local trust root before any real activation; production signing ownership remains a separate decision.

`node scripts/scan-retained-evidence.mjs` decompresses retained evidence into a temporary scan copy and runs Gitleaks. It removes only public JAR manifest entries whose attribute is `SHA-256-` plus `Digest`, and normalizes the exact Trivy package identifier formed from `org.keycloak:` plus `keycloak-crypto-fips1402`; these reproducibly trigger generic API-key false positives. The original scanner/SBOM bytes and checksums remain unchanged. Other fields, including actual synthetic credentials, are still scanned and fail the test gate.

Future publishing, signing and deployment entry points must validate their fully rendered JSON artifact **and** run an independent production High/Critical image scan. The guard accepts only schema version 1, `kind: "rendered-deployment"`, a declared production context, `rendered: true`, digest-pinned `images`, and `productionScan.required: true`; the latter is a requirement declaration, not proof of a passed scan. It rejects local Compose paths, local eligibility/dispositions and reviewed local image identities. Unsupported YAML/TOML/Terraform artifact forms fail closed until a structured renderer/validator exists. This repository has no production release pipeline yet.

Run from the repository root with Docker Compose v2:

```sh
pnpm services:config
pnpm services:up
pnpm services:status
pnpm services:down
```

`up` waits for health checks. `status` reports each service's state and health. `down` retains named volumes so the next `up` reuses local data. On first use, the helper generates independent random local credentials in the ignored `infra/docker/.local/credentials.json` (mode 0600). Keep this file local. It is a development-only bootstrap mechanism, not the approved production secrets provider. If it is lost while volumes remain, the stored database credentials will no longer match; restore the local file or deliberately recreate local data after confirming it contains no needed work.

The app, Keycloak and Temporal databases use separate PostgreSQL containers, credentials and volumes. No business tables are created. Redis is expendable. MinIO is a local S3-compatible reference; no bucket is public or created by this ticket. Keycloak and Temporal run without production TLS/auth hardening and must only be used on a trusted development machine. All service ports remain on private Compose networks; no host port is published. Application clients have no credentials or public endpoint yet.

The Keycloak `/health/ready` check runs on its internal management port. Database and Redis checks run inside their own containers. The helper runs short-lived private probes against MinIO's `/minio/health/ready` endpoint and Temporal's cluster health command. Startup and status fail when either is unavailable; Compose reports other unhealthy services. These checks are local infrastructure signals; private application liveness/readiness endpoints belong to a later API ticket. Startup/config activity is visible through minimal operational events without secrets. No domain audit or outbox event exists yet.

This composition is not a production deployment template. Production secrets/KMS, TLS/mTLS, authenticated Temporal ingress, storage encryption/locking, service grants, backup and release approval remain separate approved work and OPEN gates. Do not place real personal data in this stack.

The upstream MinIO community container registry is unavailable. The local stack uses a digest-pinned Chainguard MinIO source build. Its minimal image lacks a shell, so the helper uses a digest-pinned curl image for private readiness probes. A one-shot volume initializer grants MinIO's non-root UID access to its own local data volume. These are local reference images; provider conformance and independent production supply-chain approval remain outstanding.

The selected local PostgreSQL image is major version 18, with fresh `*-v18-data` volumes. Earlier local PostgreSQL volumes are retained by Docker and are not migrated or deleted by this ticket. The image scan gate remains active for every local image. The current Keycloak 26.7.4 image has High/Critical findings and fails the unchanged production-style container gate; a local disposition cannot alter that result. The October 6 database also reports four Redis findings. Do not use this stack for real identities or personal data.
