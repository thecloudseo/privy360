# State machines and durable execution

All transitions are commands with expectedVersion, idempotency key, deterministic permission, guard and audit/outbox event. State columns are constrained enums; arbitrary PATCH of state is forbidden. Audit event name is the command's past-tense action; EVENT_MODEL.md governs delivery. Temporal timers refer to database work item IDs; domain state remains PostgreSQL. No timer duration is asserted as law until an approved requirement/rule version supplies it. Unknown deadline produces a visible legal-review task. Timers use pinned policy version and UTC instant; a later law change proposes rescheduling and preserves original calculation.

## Workflow execution contract

Workflow key = deployment/tenant/type/business-id. One durable work item owns execution; Temporal replay cannot create a second business effect. Activities use idempotency key work-item+step+business-version and bounded retries (initial proposal 1s exponential backoff, cap 60s, max 8 automated attempts for safe transient failures). Validation/authorization errors are non-retryable. Dead-letter state visible to scoped operator, replay is a new audited command. External operations use provider idempotency or reconciliation; exactly-once delivery is never claimed.

Long-lived workflows store definition/policy version, must support old in-flight execution during deployment, and use Temporal versioning/compatible workers. Cancellation signals do not assume an external effect was undone. Compensation has explicit permission and audit; irreversible deletion cannot be compensated. Tasks and approvals reference current resource version and expire on material change. Lock/version race tests cover simultaneous approval, withdrawal, hold activation, duplicate callbacks and revoked workers.
